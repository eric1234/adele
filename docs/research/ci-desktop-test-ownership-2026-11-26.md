# Desktop test ownership audit, 2026-11-26

Role: Non-normative appendix to the [CI performance investigation](ci-performance-2026-11-26.md). Snapshot: `1367bb502cf0de1b6c161bdb057271dd07e0b8a2`. The destinations below are recommendations, not accepted architecture or maintained test policy. This is a source audit, not a timing measurement.

**Finding:** keep generic host behavior in desktop, move single-plugin behavior with the plugin, and create `adele_plugin_interactions` for assertions about **two or more concrete plugin implementations together**. The desktop can be the runner or fixture in all three cases. Moving all of `core/`, all AOT/EVC tests, or even all of `prepared_portable_git_integration_test.dart` as units would assign the wrong owners. The two Git/Diff suites and the normal application suite are good *case-splitting* candidates; moving or rehashing their existing paths alone leaves large indivisible work units.

## Basis and destinations

I compared the recursive source inventory with [desktop discovery](../../tools/test_runner.dart), inspected case registrations (including loops, helper functions and parts), imports, assertions, and the actual code or artifact supplied by consequential fixtures. The deciding question is: **what behavior would have to change to make this assertion wrong?** A stock ID in a manifest, a public contract, a real database, a fixture backend, or a second installed plugin is not by itself evidence of cooperation. Conversely, deliberate independence (e.g. one *actual* tool's presenter retires while another still renders) can be an interaction. Preserve both positive and negative assertions.

Authority: [app ownership](../../app/README.md#ownership), [architecture overview](../architecture/overview.md), [dependency rules](../architecture/dependency-rules.md#application-composition), [plugin system](../architecture/plugin-system.md), [product model](../architecture/product-model.md), [testing procedure](../development/testing.md#maintained-test-targets). In particular, Git owns comparison/index semantics and worktrees, Diff owns the public change/review contracts, its drafts and presentation, Chat owns conversation/projection/sequencing, and Evaluator intentionally reads other owners' retained schemas. See the [Git](../../plugins/git/README.md), [Diff](../../plugins/diff_viewer/README.md), [Chat](../../plugins/chat_strategy/README.md), and [Evaluator](../../plugins/session_evaluator/README.md#ownership) maps. Current development guidance keeps multi-plugin integration in `adele_desktop`; the independent target is the requested **change** to test ownership, not a change to that production architecture.

The inventory uses these destination rules. A group label in backticks is a case-title fragment or code anchor for a reviewer, not a `--name` filter to bake into CI.

| Key | Concrete proposed location and runner |
| --- | --- |
| **C** | Keep the file or remaining host cases at the original `app/test/` path in `adele_desktop`. Owns composition, exact authority/retirement, native primitives, shell, invocation gates, host persistence, and app lifecycle. |
| **P(plugin)** | Use `plugins/<plugin>/packages/frontend/test/desktop/` for hosted Flutter cases where there is a suitable existing frontend test target. Use the corresponding plugin `packages/backend/test/` or root `test/` for cases that actually run under plain `dart test` (substitute `package:test` only where equivalent). For real desktop-backed coverage of a backend-only implementation with no suitable Flutter target, use a **test-only** `plugins/<plugin>/packages/desktop_tests/test/` Flutter workspace member, e.g. `plugins/git/packages/desktop_tests/test/git_task_anchor_store_test.dart` (`git_desktop_tests`); do not put Flutter files in the seven plain-Dart `git_backend` shards. This alternative is for a concrete harness need, not one new package per table row. |
| **I(area)** | New independent `adele_plugin_interactions` target, working directory `app`, source root **`app/plugin_interactions_test/<area>/`**, *outside* `app/test/`. Reuses the existing private Flutter package and test dependencies; no interaction library or production-facing package. For example `app/plugin_interactions_test/review/diff_git_approval_test.dart` and `app/plugin_interactions_test/execution/command_output_capture_integration_test.dart`. A `support/` subdirectory may hold the harness's own tests; do not count these as production-plugin interactions. |

Within a destination retain the source basename when moving a whole file; use a distinct descriptive `*_test.dart` per coherent group when splitting. Below, short owner names are the directory names under `plugins/`: Diff = `diff_viewer`, Chat = `chat_strategy`, Filesystem = `filesystem_tools`, Command = `command_tools`, Search = `search_tools`, Agent = `agent_configuration`, Model = `model_configuration`, Browser = `task_browser`, Source = `source_editor`, Policy = `conservative_tool_policy`, Local Directory = `local_directory_project`, Evaluator = `session_evaluator`. Each has one semantic owner even when the same plugin's frontend, backend and contract participate. A backend scenario run with a plugin-local Flutter harness is still a backend integration test. Do not make the backend depend on its frontend.

## Discovery, migration and verification

1. **Introduce one disjoint root, not a second registry of filenames.** Generalize `TestTarget` / `partitionTestFiles` in [test_runner.dart](../../tools/test_runner.dart) to accept a target-relative discovery directory (default `test/`). In [tools/adele.dart](../../tools/adele.dart), select that root for **both** unsharded and sharded execution. An unqualified `flutter test` in `app` only selects `test/`; conversely `flutter test <entire-dir> <shard-files>` would run too much. Pass the directory *or* the selected sorted paths, never both. Use `*_test.dart`, recursive discovery, no traversal of linked directories, normalized package-relative paths, deterministic disjoint partitions and fail on an empty explicit selection. Test this with a real moved file in the first slice. Do not just nest `interactions/` inside `app/test/` and hope unsharded desktop omits it.

**Limitations and decisions to confirm.** These are ownership recommendations; none of these moves, target names, package manifests, or runner flags has been implemented or executed here. Boundaries least suited to mechanical splitting are a real plugin's effect racing a host revocation, normal application shutdown with pending plugin work, and a stock declaration used to prove both a plugin default and a generic Settings rule. Keep the strongest existing integrated assertion once, at the owner of its distinguishing failure, rather than duplicating slow full startup in both targets. Confirm that a proposed plugin-local package really runs under Dart vs Flutter before reusing its target. Adding jobs or extracting groups can repeat `setUpAll` compilation; this inventory establishes ownership and candidate split points, **not** a speedup, optimal shard count, or lower aggregate runner cost. Measure on CI after migration before assigning duration weights, without weakening full captures or relaxing deadlines.
